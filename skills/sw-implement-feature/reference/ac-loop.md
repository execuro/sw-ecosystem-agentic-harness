# The per-AC loop

Entered once per acceptance criterion, by the agent the delegation table routed it to. Steps 1-5 run in order; none is optional.

For each AC:

1. **Test first.** Write the test(s) the spec defines for this AC — unit/integration, and, when the AC is user-facing, the e2e scenario the spec planned for it too. Do not defer writing the e2e test to `sw-verify-feature` — it is written now, alongside the unit/integration tests, so it exists to run in step 4. Confirm they fail for the right reason.
2. **Implement.** Write the minimum code to satisfy the spec's architectural decision for this AC.
3. **Conform.** Before running tests, bring this AC's new/changed code in line with Shopware's own toolchain, so conformance issues are caught and fixed while the AC is still open, not accumulated until `sw-verify-feature`'s final pass. If step 0's table shows the shopware-cli row unticked, skip this whole step for this AC and say so once, not per-AC — installing it is not this skill's job. Otherwise, scoped to `custom/plugins/<PluginName>` (or the narrower directory this AC actually touched):
   - **Fix** (mutates code) — `shopware-cli extension fix --only <tools> custom/plugins/<PluginName>`, using only the tools that have a real `Fix()` in shopware-cli's own source (confirmed from `internal/verifier/*.go`): `eslint`,`stylelint` for Admin/Storefront JS/SCSS this AC touched, `rector` for PHP changes, `admin-twig` for Administration Twig templates, `symfony-xml` if the AC left a `services.xml`/`routes.xml` behind. Do **not** put `php-cs-fixer` or `phpstan` in this `--only` list — their `Fix()` is a no-op in shopware-cli; nothing will happen and it wastes a run.
   - **Format** (style-only, still mutates) — `shopware-cli extension format --only <tools> custom/plugins/<PluginName>`, using `php-cs-fixer` for PHP changes and/or `prettier` for JS/JSON changes this AC touched — these two only do real work through `format`, not `fix`.
   - **Validate** (read-only check, must fix anything it reports by hand) — `shopware-cli extension validate --full --only=phpstan,eslint,stylelint custom/plugins/<PluginName>` scoped to the areas this AC touched (PHP → phpstan; Admin/Storefront JS → eslint; SCSS → stylelint). **`--only` has no effect without `--full`** — passing `--only` alone silently resets to the default `sw-cli` structural check and none of these three run; always pass both flags together. Fix anything it reports before moving on — do not defer a known conformance error to the end-of-feature verification pass.
   - This three-step sequence is a lighter, per-AC version of the full gates `sw-verify-feature` runs at the end (`sw-verify-feature-code-quality` for phpstan/eslint/stylelint at whole-plugin scope, `sw-verify-feature-architecture` for the `admin-twig`/`storefront-twig` read-only Twig lint gate); it exists to prevent surprises there, not to replace it. `sw-cli` itself (the default structural/manifest validation) and `storefront-twig` (no real `Fix()`) are check-only tools this skill never runs — that's `sw-verify-feature`'s job.
4. **Confirm.** Run only the test(s) relevant to this AC (and any test it could plausibly have broken) — never the full suite mid-implementation. If they fail, fix the implementation, not the test, unless the test itself is wrong relative to the spec.
   - **Run this AC's acceptance test now, not later.** Do not wait for the end-of-feature `sw-verify-feature` run to be the first time an AC's acceptance-level test executes. If the AC is user-facing and has an e2e scenario, execute it immediately after the unit/integration tests pass: spawn `sw-qa-engineer` with the spec path, this AC's id, the detected Shopware/PHP version and evidence, and the e2e scenario written in step 1, and have it run that scenario now via the Playwright MCP tools. Treat a failure here exactly like a failing unit test — the AC is not done until it passes.
   - This means every AC leaves this loop already proven at both levels (unit/integration and acceptance/e2e). `sw-verify-feature`'s job at the end is to audit and re-confirm across the whole feature, not to be the first execution of any AC's test.
5. **Scope check.** Run `git diff --stat` for this AC's changes. Every file listed must be explained by this AC's §3 plan or an existing §6 Decision Log entry — anything else gets reverted or added to §6 with a one-line reason before moving to the next AC.

If the AC's data is exposed through more than one interface (Admin UI, Storefront, Store API, Admin API), the test(s) for it must check the real shape of **every** interface touched — rendered HTML, raw JSON response — not only a PHP entity accessor. Accessor methods can return a value through a fallback (e.g. an extension bag) that the actual serialized/rendered output does not expose the same way; a test that only calls `->get()` can pass while the feature is broken for every real consumer.

Do not deviate from the spec's technical decisions. If the spec is ambiguous or wrong for a given AC, escalate to `sw-shopware-architect` (see above) rather than inventing a different technical approach. **Stop after the first workaround, not after several:** if satisfying an AC requires decorating, subclassing, or overriding a framework-internal class or service that the spec did not name, treat that as "the spec is wrong for this AC" immediately. Do not add a second override to patch a side effect of the first — report back instead of stacking fixes.

If the spec's plan touches the database schema (migration, new table/column), run that migration against every environment the feature will be checked in before any manual or live check — not just the environment the automated test suite bootstraps for itself. A migration applied only where tests auto-provision it, and not in the environment used for manual verification, produces confusing "column/table not found" failures that look like implementation bugs.
