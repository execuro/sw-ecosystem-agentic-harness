# Editor mode

Entered when invoked as `<spec path> --editor-session <url> --batch <batch.json>` — one note batch from the page. The session's editable document is always the tech spec; the PRD is reference only. Decides how the procedure differs from the terminal flow: no interactive questions, scoped re-verification, and progress emission.

Same procedure/boundary/verification/ADR rules, plus:

- **Scoped.** Nothing on open. Continue mode: read the batch first, run step 3 only for touched mechanisms, edit only named blocks plus invalidated ones, re-evaluate §7 — no re-verification/new §6 for untouched ACs. Full pass only on an explicit review or draft request, **or when the spec still has no ACs in §3** (§0 drafts before hand-off, so that is a fallback) — that batch runs the complete flow, step 0.5 and version detection included.
- **No terminal questions.** Never ask via a structured question tool (Claude Code: `AskUserQuestion`; Codex: `request_user_input`). Every ask → §6 block: `**Q-n**`, 2–4 `- [ ]` options, one `(recommended)`, agent notes `  - [<agent>] <stance>: <reason>` under the judged option. Max 6/run. Tags: `[adr] <title>` → `A: Extract` / `B: Keep`; `[gate] Open ADRs <ids>` → `A: Wait (recommended)` / `B: Override`; step-0.5's two `[gate]` titles verbatim → `A: Bootstrap first (recommended)` / `B: Proceed unverified`. Unanswered `[gate]` → *In progress*, never auto-override.
- **Batch input.** Ticks first — a ticked question with no note is still an answer. `answer`/`[x]` tick → anchor, append Decision Log, delete block (`[adr]` sub-step 3, `[gate]` sub-step 5). `comment`/`free` → this run's briefing (block-bound `path`/`line`–`endLine`/`md`/`quote`/`hash`; verify `md` matches, fall back to `quote`; `selection` → rework only that text). `diagram` → update the graph file. *What*/*why* notes belong to the PRD: read it freely — `batch.reference.path` — as the source of truth for reconciliation, but it is **read-only** here, a separate session's document. Never write it, never anchor an answer into it, never emit against it; report the note in the reply ("this changes FR-4 — take it to the PRD session, `sw-design-requirements <prd path> --editor`") and change nothing. First write migrates a pre-template spec or an AC-less stub; blocks get missing options only when touched.
- **Scoped runs.** Re-spawn architect only for an overturned/new decision, QA only for a changed test plan, `sw-product-manager` only for feasibility — together still one message; else edit/verify/anchor/log alone, name agents. **Light batch** — every note is an `answer` or a tick, or the batch is chat only: no step 3 and no verification spawn, the user is waiting on the page for what is a bookkeeping run.
- **Advice is part of raising a question, not a later phase.** A §6 block this run raises is advised before the run finishes — every batch, a light one included. *Light batch* drops step 3, never the advisory spawn, and never wins over this rule: an answers-only batch is exactly the batch that raises the next round, so its questions are the ones that must not be born unadvised. Never mark `(recommended)` on your own judgement — an agent recommends, this skill records. **Exception:** `[adr]` and `[gate]` blocks keep the pre-canned options above (`A: Extract`, `A: Wait (recommended)`, `A: Bootstrap first (recommended)`) and need no spawn; they are procedure, not judgement.
- **Reply first, then advise.** 1. `emit chat` the anchored report — changed blocks, answers, §7 — so the page has it while the advisor runs; the run stays active. 2. `emit progress "advising Q-7–Q-9"`. 3. One batched advisory brief per agent, one message: question sentences and options verbatim, spec path, version + evidence; ask for the option and a one-line reason — a verdict, not research, and never one spawn per question. `sw-shopware-architect` advises every raised question, `sw-product-manager` in addition where an option turns on stock Shopware behaviour; QA keeps its own trigger. 4. Write the `(recommended)` mark and the `  - [<agent>] <stance>: <reason>` notes; disagreement → keep the architect's mark, both notes. Advised and declined → no mark, `[architect] no recommendation — project preference`; the user's own question → `[user] raised on the page — advice not requested`. 5. `emit done` with the final report.
- **Preserve:** status tags (`- **AC-2** [partly] (FR-3)`, `- **Decision:** [done] …`), `Diagram:` line, §6 blocks/ticks — rewrite in place, never regenerate.
- **Diagrams.** `specs/NNNN-slug-spec.architecture.graph.json`; run `npx -y @execuro-sw-ecosystem/sw-specs-editor@latest diagram specs/NNNN-slug-spec.architecture.graph.json specs/NNNN-slug-spec.architecture.excalidraw`, keep §2's `Diagram:` line — never write it directly.
- **Progress.** `npx -y @execuro-sw-ecosystem/sw-specs-editor@latest emit --since <step-0.5 start> progress "<step>" --batch <id> --doc <spec path>` (`--doc` is the document path: it names the session, and a feature's PRD and spec are two of them) before/after each step/spawn; `--since` prefixes `+m:ss`. Keep them few and short — one line per phase, under ~60 characters, no per-tool narration. They are the page's only sign of life while a spawn runs, not a log.
- **Report:** changed blocks; answers (Q ids → anchor); first unmet §7 criterion or `none`; status/confidence/`Open ADRs`; `Advised: <Q ids> (<agents>)` or `Advised: none`; `Agents: <list or none>`; `Timing:`. Advised and Agents are mandatory every run, not only when an agent ran.

Graph shape: `{ title, direction: "LR", groups: [{id,label}], nodes: [{id,label,type: entity|actor|service|external|event|store,group?,note?}], edges: [{from,to,label?}] }`.
